# Konveyor / MTA — Agentic Migration Prototype

An agentic-migration extension of the Konveyor Tackle UI. On top of the full
Migration Toolkit for Applications (MTA) experience, it adds:

- **Agents** — create and configure AI agents that assist with migration work.
- **Migration Plans** — build multi-stage migration plans (the "migration
  workflows" area of the app).
- **Skills & Skill collections** — manage reusable skills that agents draw on,
  and group them into collections.
- **Models** — manage the underlying models available to agents.
- **Plan Runs** — kick off and track runs of a migration plan, including
  commit-level activity, from the application inventory and application
  detail pages.

Everything else (application inventory, assessments, archetypes, migration
waves, reports, etc.) is the standard Tackle UI, unmodified in behavior.

## What this is

This prototype is a fork/snapshot of [`konveyor/tackle2-ui`](https://github.com/konveyor/tackle2-ui)
plus the Agentic Migration feature work on top of it, repackaged to run as a
fully static, self-contained build for GitHub Pages hosting alongside the
other prototypes in this repo.

## How it's built

- **Webpack** (not Vite) + **react-router-dom v5** — this is a direct import
  of a large, pre-existing app; rewriting its bundler or router major version
  was out of scope. Each prototype in this repo is served from its own
  isolated subfolder with no shared runtime, so this doesn't conflict with
  other prototypes.
- **MSW, `MOCK=full`** — all API traffic is served from an in-browser mock
  service worker. There is no backend, no Keycloak, and no `TACKLE_HUB_URL`,
  matching every other prototype in this repo.
- `window._env` (which the real app normally gets from a small Express
  server / `entrypoint.sh` at container start) is instead **baked into
  `index.html` at build time** by `config/webpack.prod.ts`, fixed to
  `MOCK=full` / `AUTH_REQUIRED=false`.
- The app is built with `PUBLIC_PATH=/AppDev-UX-Prototypes/mta-agentic-migration/`
  so all absolute asset URLs, the router `basename`, the mocked `/hub` API
  prefix, the MSW worker scope, i18n resource loading, and the template
  download links resolve correctly under that GitHub Pages subpath.
- `dist/404.html` is a copy of `dist/index.html` (generated by a `postbuild`
  script). Note this repo's GitHub Pages site only honors a single
  **root-level** `404.html` (the launcher's), so — same as the existing
  `prototypes/mta` prototype — a hard refresh or direct link to a deep client
  route (e.g. `/mta-agentic-migration/agentic-migration/agents`) will show the
  site's top-level 404 page rather than this app. Navigating via the app's own
  links/nav (including the "Back to all prototypes" bar) always works
  correctly. Fully solving deep-link refreshes site-wide would mean adopting
  the [rafgraph/spa-github-pages](https://github.com/rafgraph/spa-github-pages)
  redirect trick in the root `404.html`, which is out of scope here.

See the root [`CONTRIBUTING.md`](../../CONTRIBUTING.md) for how this
prototype is built and deployed alongside the others in this repo.

## Local development

```bash
npm install
npm run build
npx serve dist -l 3000
```

Note: because the production build is baked for the
`/AppDev-UX-Prototypes/mta-agentic-migration/` subpath, serving `dist/`
directly at the root of a local server won't resolve assets correctly —
proxy it under that same subpath (e.g. via a reverse proxy or
`serve -s dist --single` under a matching path) to fully verify subpath
routing, or use `client`'s own `npm run start:dev` for root-path local
development without the GitHub Pages path prefix.

## Heads up

The bundle is fairly large — Monaco editor worker chunks push it to several
megabytes. That's acceptable for GitHub Pages, but worth knowing about if you
notice a slower initial load than the other, smaller prototypes here.
